## Build sequence item 1: warehouse schema + Alembic migrations

**Files**: `app/warehouse/schema.py`, `app/warehouse/__init__.py`, `migrations/` (new, Alembic async

**What matches `docs/PLAN.md` §4 exactly**: every table, column, constraint, and index from the plan's DDL,
translated 1:1 into SQLAlchemy Core `Table` objects (not ORM classes — see the module docstring for why:
bulk-COPY-friendly, matches the plan's bulk-upsert requirement). `cell_status` is a native Postgres ENUM.

**Real deviations found only by actually running this, not by re-reading the plan:**

1. **Alembic's autogenerate detected LangGraph's own checkpoint tables (`checkpoints`,
   `checkpoint_writes`, `checkpoint_blobs`, `checkpoint_migrations`) as "removed"** — they live in the same
   Postgres database (`docker-compose.yml`'s single `postgres` service) but aren't part of
   `app.warehouse.schema.metadata`, so a naive `alembic upgrade head` would have dropped them. Stripped the
   generated `drop_table`/`create_table` calls for those four tables by hand from both `upgrade()` and
   `downgrade()`, with a comment explaining why, so this migration chain never touches tables it doesn't
   own. **Verified this was necessary and now correct**: ran `alembic downgrade base` then
   `alembic upgrade head` against the real local Postgres and confirmed via `\dt` that the four checkpoint
   tables were present and untouched throughout, while all 18 new tables were cleanly created and dropped.

2. **The autogenerated migration referenced the same Postgres ENUM type (`cell_status`) inline on three
   different columns, each with SQLAlchemy's default `create_type=True`** — running it as generated issued
   `CREATE TYPE cell_status` three times and failed with `DuplicateObjectError` on the second. Tried
   `Enum.create(bind, checkfirst=True)` first; it still attempted a duplicate `CREATE TYPE` against the
   async driver in this environment (unreliable existence-check, not investigated further since a more
   robust fix exists). **Fixed** with the standard Postgres `DO $$ BEGIN CREATE TYPE ... EXCEPTION WHEN
   duplicate_object THEN null; END $$;` idiom (Postgres has no native `CREATE TYPE IF NOT EXISTS`), creating
   the type exactly once and referencing it everywhere else with `create_type=False`.

3. **`migrations/env.py` originally resolved `DATABASE_URL` via `app.settings.get_settings()`** (reusing
   the existing app-wide settings object, seemed like the natural "config from environment, no duplicated
   logic" choice). **Live-verified this was wrong**: building the real Docker image and running
   `python -m alembic current` inside it failed — `get_settings()` requires `comtrade_api_key` and
   `gemini_api_key` too, both required fields of the existing, unrelated trade-analysis feature's
   `Settings` model. A migration runner has no business needing Gemini/Comtrade credentials just to find a
   database URL. **Fixed** by reading `DATABASE_URL` directly from `os.environ` in `env.py`, with the same
   default (`sqlite+aiosqlite:///./local.db`) `Settings.database_url` uses, for parity without the coupling.
   Re-verified inside a freshly rebuilt image: `alembic current` now succeeds with only `DATABASE_URL` set.
